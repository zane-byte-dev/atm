# 记忆候选判定样例

这些样例用于处理边界，不是固定关键词表。核心问题是：这条信息跨会话是否仍有用、是否已被确认、是否有更合适的事实源。

| 会话内容 | 动作 | 理由 |
|---|---|---|
| 用户确认“hub 就是 mm-dio-hub-service，以后直接说 hub” | `remember`，kind=`alias` | 稳定映射能帮助所有 Agent 路由后续请求 |
| 用户确认“ATM 不内置 LLM，Agent 按 skill 整理会话” | `remember`，kind=`decision` | 已确认的项目方向会影响后续实现选择 |
| 助手建议删除 HTTP，但用户没有回应 | `reject` | 仍是助手提案，不是已作出的决定 |
| “CR 35005479 正在发布，Run 52608474 构建中” | `reject` | 单次运行状态很快失效，应留在 TODO/CR |
| “Windows `.exe` 上传失败时优先排查 multipart 白名单” | memory 或 knowledge | 一句话触发器可进 memory；完整服务约束和诊断步骤应进应用 knowledge |
| 应用 ID、环境 ID、六条发布流水线和仓库地址 | `knowledge` | 结构化、需要引用和持续维护，不应拆成多条 memory |
| “`atm todo done` 会更新 Markdown 状态” | 通常 `reject` | 能从当前代码和 help 廉价验证，写入 memory 容易过期 |
| `~/.agents/skills/atm` 当前是某路径的软链 | 通常 `reject` | 环境可直接检查；只有它是跨 Agent 故障恢复关键约定时才考虑记录 |
| 已存在完全相同的 hub alias memory | `duplicate` | 不重复追加事件 |
| 旧记忆说默认分支是 `master`，用户核验后改为 `main` | `supersede` | 同一稳定事实发生变化，需要保留替换历史 |

## 可信度提示

- `high`：用户明确表达或确认；平台/代码核验结果随后得到用户接受。
- `medium`：助手声称已通过工具核验，但 transcript 中没有用户确认；可以预览，写入前宜复核。
- `low`：助手建议、推断、未完成计划或互相矛盾的说法；不写入。

## 合并与拆分

- 同一对象的“别名 + 路由提示”可以合成一条，例如“hub 指代应用 X，详细发布信息查 X 的知识卡”。
- 不把架构决定、个人偏好、发布状态和诊断步骤拼成一条长记忆。
- 多轮会话共同确认同一事实时，选择最直接的用户确认作为主来源；必要时在内容中保持简洁，不罗列所有 session。
